# Personalized Product XML Worker

Cloudflare Worker для генерації тестового XML-фіду з персоналізованими товарами.

Основне призначення — тестування імпорту та оновлення товарів із контрольованими змінами категорій, характеристик, цін, брендів, країн, зображень, а також сценаріїв із порожніми або відсутніми характеристиками.

**Production endpoint:**

`https://product-xml-worker-personalized.y-rubtsova.workers.dev/products.xml`

Worker використовує реальні тестові довідники категорій, характеристик, допустимих значень характеристик, брендів і країн.

Категорії беруться з `merchant_categories.xml`, який локально перетворюється у компактний `generated-categories.json`. Це потрібно для того, щоб Cloudflare Worker не парсив великий XML під час startup.

Для тестових назв та описів використовуються українські значення. Поля `name_ru` і `description_ru` наразі дублюють український текст:

```xml
<name_ua>...</name_ua>
<name_ru>...</name_ru>
<description_ua>...</description_ua>
<description_ru>...</description_ru>
```

## Детермінованість

### `idSeed`

`idSeed` визначає базовий набір товарів. Один і той самий `idSeed` відтворює той самий baseline: ID товарів, категорії, category ID, характеристики, значення характеристик, бренд, країну, ціни, зображення, назви та описи.

Якщо `idSeed` не переданий, Worker створює випадковий UUID, тому запит генерує новий набір товарів.

### `changeSeed`

`changeSeed` визначає конкретну детерміновану версію змін поверх baseline. Це дозволяє моделювати декілька послідовних update-state для тих самих product ID:

```text
baseline
↓
changeSeed=1
↓
changeSeed=2
↓
changeSeed=3
```

Повторне відкриття абсолютно однакового URL повертає той самий результат.

## Робота кількох QA одночасно

Для паралельної роботи кількох QA не потрібно створювати окремий Cloudflare Worker для кожного користувача.

Worker є stateless і не зберігає стан між запитами, тому вся команда може використовувати один production endpoint:

```text
https://product-xml-worker-personalized.y-rubtsova.workers.dev/products.xml
```

Щоб тестові дані різних QA не перетиналися, кожен користувач має використовувати унікальний `idSeed`.

### Рекомендований формат `idSeed`

```text
idSeed=<qa-name>-<ticket>
```

Наприклад:

```text
idSeed=jane-PB-1234
idSeed=anna-PB-1234
idSeed=olena-PB-9801
```

Повний приклад URL:

```text
https://product-xml-worker-personalized.y-rubtsova.workers.dev/products.xml?count=20&categories=8&idSeed=jane-PB-1234
```

Інший QA може одночасно використовувати:

```text
https://product-xml-worker-personalized.y-rubtsova.workers.dev/products.xml?count=20&categories=8&idSeed=anna-PB-1234
```

Різні `idSeed` генерують різні:

* product ID;
* category ID;
* baseline-дані;
* характеристики;
* бренди;
* країни;
* ціни;
* зображення;
* назви та описи.

> Якщо два QA використовують однаковий `idSeed`, вони працюватимуть з одним і тим самим детермінованим набором товарів.

### Послідовні оновлення одного набору товарів

Для тестування кількох update-state потрібно залишати той самий `idSeed` і змінювати `changeSeed`.

Baseline:

```text
https://product-xml-worker-personalized.y-rubtsova.workers.dev/products.xml?idSeed=jane-PB-1234
```

Перше оновлення:

```text
https://product-xml-worker-personalized.y-rubtsova.workers.dev/products.xml?idSeed=jane-PB-1234&change=price&changeSeed=1
```

Друге оновлення:

```text
https://product-xml-worker-personalized.y-rubtsova.workers.dev/products.xml?idSeed=jane-PB-1234&change=price&changeSeed=2
```

У всіх цих запитах product ID залишаються тими самими, а поля, передані через `change`, можуть отримувати нові детерміновані значення залежно від `changeSeed`.

### Рекомендований підхід для команди

Для звичайного тестування:

```text
idSeed=<qa-name>-<ticket>
```

Для послідовних оновлень:

```text
changeSeed=1
changeSeed=2
changeSeed=3
```

Окремий Cloudflare Worker потрібен лише у випадку, якщо потрібно:

* змінювати сам код генератора;
* тестувати окрему версію Worker;
* мати незалежний deployment;
* не залежати від спільного production Worker.


## Характеристики

- Для товару використовуються тільки характеристики його `portal_id`.
- Для `singleselect` обирається одне допустиме значення.
- Для `multiselect` обирається від 1 до 5 різних допустимих значень.
- Характеристики типу `unknown` не додаються у generated data.
- Якщо одна характеристика повторюється у source XML, її значення об'єднуються та дедуплікуються під час генерації `generated-categories.json`.

### Forced value для характеристики

Для негативних або edge-case сценаріїв можна примусово передати значення характеристики, якого немає в системному довіднику.

Наприклад:

```text
https://product-xml-worker-personalized.y-rubtsova.workers.dev/products.xml?categories=8&idSeed=test-1&setCharacteristic=Колір:Elantra
```

## Категорії

Категорії задаються через `portal_id`. Можна передати одну або декілька категорій. Якщо передано декілька, товари розподіляються між ними максимально рівномірно. Один товар завжди має рівно одну категорію.

Якщо параметр `categories` не переданий, категорії детерміновано обираються з усіх доступних категорій.

Генерований `categoryId` не є сталою властивістю категорії: він залежить від `idSeed` та `portal_id`. Тому в довіднику категорій нижче наведені `portal_id` і назва категорії з source XML.

## Назви та описи

Назви та описи генеруються детерміновано на основі категорії, бренду, характеристик та індексу товару. Для назви пріоритет мають характеристики на кшталт `Тип`, `Вид`, `Смак`, `Аромат`, `Колір`, `Розмір`, `Об'єм`, `Вага`, `Кількість`, `Кількість в упаковці`, `Призначення`, `Матеріал`, `Форма`.

Для гарантії унікальності назва містить суфікс `TEST-N`.

При `change=...` назва та опис навмисно **не регенеруються**. Це дозволяє тестувати часткове оновлення конкретних полів товару незалежно від текстових полів.

## Обмеження та правила

| Обмеження / правило | Поведінка |
|---|---|
| Endpoint | Worker обробляє тільки `/products.xml`. Інші paths повертають `404 Not Found`. |
| `count` | Тільки ціле число від `1` до `100`. |
| `count` за замовчуванням | `10`. |
| Максимальна кількість товарів | `100`. |
| Кількість категорій | Якщо передано декілька `categories`, `count` має бути не меншим за кількість унікальних категорій. |
| Невідомий `portal_id` | HTTP `400`. |
| Дублікати категорій | `categories=8,8,9` автоматично дедуплікується до `8,9`. |
| `idSeed` | Може бути будь-яким непорожнім рядком. |
| Порожній `idSeed` | HTTP `400`. |
| Відсутній `idSeed` | Генерується випадковий UUID, тому кожен запит може створити новий набір товарів. |
| `changeSeed` | Може бути будь-яким непорожнім рядком. |
| `changeSeed` за замовчуванням | `"1"`. |
| Порожній `changeSeed` | HTTP `400`. |
| Підтримувані `change` | `price`, `brand`, `country`, `images`, `category`, `characteristics`. |
| Невідоме значення `change` | HTTP `400`. |
| Дублікати у `change` | Автоматично видаляються. |
| `change=price` | Змінюються і `price`, і `old_price`; `old_price` залишається більшим за нову ціну. |
| `change=brand` | Новий бренд відрізняється від baseline, якщо існує альтернатива. |
| `change=country` | Нова країна відрізняється від baseline, якщо існує альтернатива. |

## Оновлення категорій

Великий source XML не парситься безпосередньо у Cloudflare Worker.

Після оновлення:

```text
src/data/merchant_categories.xml
```

потрібно локально виконати:

```bash
node scripts/generate-category-data.mjs
```

Скрипт створить або оновить:

```text
src/data/generated-categories.json
```

Саме цей компактний JSON використовується Worker у production. Після зміни source XML потрібно закомітити оновлений `generated-categories.json`.

## Локальний запуск

```bash
npm run dev
```

Локальний endpoint:

`http://localhost:8787/products.xml`

## Production

`https://product-xml-worker-personalized.y-rubtsova.workers.dev/products.xml`

Deployment виконується через Wrangler:

```bash
npx wrangler deploy
```

GitHub repository підключений до Cloudflare Workers Builds, тому push у `main` запускає новий deployment.
